# 보안 및 운영 고려사항

웹훅 디버거는 외부에서 들어오는 임의의 HTTP 요청을 받습니다. MVP라도 보안과
운영 경계를 처음부터 고려해야 합니다.

## 데이터 보호

- UI에서 `Authorization`, `Cookie`, `Set-Cookie` 같은 민감 header 마스킹
- 원본 payload는 디버깅에 필요한 기간 동안만 저장
- 임시 URL이 계속 활성화되지 않도록 endpoint 만료 기능 추가
- 배포 환경에서는 HTTPS 사용

## 접근 제어

- endpoint 소유자만 수신 요청을 볼 수 있어야 함
- endpoint UUID는 길고 추측하기 어려워야 함
- 삭제된 endpoint는 더 이상 요청을 받지 않아야 함

## 요청 안전성

- 저장소와 메모리 보호를 위해 request body 크기 제한
- endpoint별 저장 요청 수 제한
- public hook URL에 rate limit 적용
- 수락/거절된 요청에 대해 예측 가능한 status code 반환

## 재전송 안전성

사용자가 backend로 임의의 내부 주소를 호출하게 만들 수 있으면 재전송 기능은
위험해질 수 있습니다. 이를 SSRF 위험이라고 합니다.

MVP 안전 기준:

- production에서 `localhost`, `127.0.0.1`, private IP range, link-local
  address를 replay target으로 차단
- target URL은 `http` 또는 `https`만 허용
- connection timeout과 response timeout 설정
- 디버거 자체의 민감 header는 자동 전달하지 않음

## 운영

- application log에는 전체 민감 payload가 아니라 request metadata 위주로 기록
- 기본 health check endpoint 유지
- request body를 DB에 저장한다면 disk usage 모니터링
- 만료된 endpoint와 오래된 request를 정리하는 cleanup job 정의
